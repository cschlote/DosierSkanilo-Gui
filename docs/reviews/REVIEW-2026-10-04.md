## Review B — Current Independent Assessment

Source: current assessment after switching model, including an independent
subagent review.

> **Unabhängige Einschätzung**
>
> Die beiden Projekte sind insgesamt in einem guten, weit fortgeschrittenen Zustand. Die Architekturentscheidung ist richtig:
>
> - `DosierSkanilo` kapselt SQLite, Scanning, Metadaten, Analyse und JSON-Transfer.
> - `DosierSkanilo-Gui` bleibt eine GUI-Schicht mit source-agnostischer Projektion.
> - Die GUI greift nicht direkt auf SQLite zu.
> - JSON und SQLite sind beim Lesen bereits weitgehend vereinheitlicht.
>
> Die aktuelle Kernlücke ist klar: Die GUI ist ein leistungsfähiger Read-only-Browser, aber noch kein Client für Scan-, Metadaten- und Analyseoperationen.
>
> **Wichtigste technische Risiken**
>
> 1. **Cancellation existiert im Repository-Pfad noch nicht.**  
>    `Repository.scan()`, `updateMetadata()` und `analyze()` sind synchrone Methoden ohne Control- oder Progress-Parameter (`source/dosierskanilo/repository/repository.d:396-417`).
>
> 2. **Der SQLite-Scan ist transaktional, aber ohne Checkpoints.**  
>    Die gesamte Dateisystemiteration läuft zwischen `begin()` und `commit()` (`repository/scanner.d:21-64`). Das ist für atomare Konsistenz gut, muss aber für Abbruchsemantik bewusst erweitert werden.
>
> 3. **Metadata ist zwar parallel, aber nicht abbrechbar.**  
>    Batches werden geplant, anschließend mit `workForce()` vollständig abgearbeitet (`repository/metadata.d:172-252`). Ein Token allein reicht hier nicht; Scheduling, Worker und Persistierung müssen gemeinsam betrachtet werden.
>
> 4. **Teilresultate sind noch nicht fachlich entschieden.**  
>    Besonders bei Metadaten und Analyse muss feststehen, ob bereits abgeschlossene Blobs/Phasen erhalten bleiben oder der gesamte Vorgang zurückgerollt wird.
>
> 5. **Schreibserialisierung fehlt noch als zentrale Eigenschaft.**  
>    Separate Leserverbindungen lösen das GUI-Leseproblem, verhindern aber nicht zwei konkurrierende Schreiboperationen auf dasselbe Repository.
>
> **Bewertung der Planung**
>
> WP-08 ist sinnvoll geschnitten. Die drei offenen Tests sind klein, unabhängig und schließen reale Lücken:
>
> - Parser-Isolation und ungültige Optionskombinationen
> - echter `dataVersion: 2`-Import
> - relationship-closed filtered export
>
> WP-09 ist in der Reihenfolge richtig:
>
> `09.1 Vertrag -> 09.2 Backend -> 09.3 CLI / 09.4 GTK -> 09.5 Parität`
>
> Allerdings ist **WP-09.2 als Umsetzungspaket zu groß**. Es enthält derzeit SQLite-Scan, fünf Metadatenarten, Analyse, JSON-Services, Cancellation, Persistenzregeln, Kompatibilitätswrapper und Concurrency-Verhalten. Als Programmabschnitt ist das okay, als einzelner Entwicklungsschritt zu breit.
>
> **Meine Empfehlung**
>
> 1. Den aktuellen GUI-P0 abschließen und tatsächlich testen. Die Änderungen sind noch uncommittet und ausdrücklich als „not yet verified“ markiert.
> 2. WP-08.1 bis WP-08.3 als separate kleine Backend-Commits erledigen.
> 3. WP-09.1 nicht nur abstrakt planen, sondern mit einer minimalen vertikalen Operation beginnen: zunächst `scan`, mit Request, Progress, Cancellation, Terminalzustand, Commit-/Rollback-Semantik und API-Tests.
> 4. Danach WP-09.2 in kleinere technische Pakete teilen: SQLite-Scan, SQLite-Metadaten, SQLite-Analyse, JSON-Scan/Analyse.
> 5. Erst wenn die CLI über diesen Vertrag läuft, die GTK-Taskverwaltung beginnen.
>
> **Gesamturteil**
>
> Die Planung ist deutlich besser als zuvor und für externe Zweitmeinungen geeignet. Sie benennt jetzt die richtigen Probleme und Abnahmekriterien. Der einzige wesentliche Verbesserungspunkt ist die Granularität: WP-09.2 sollte vor der Implementierung noch in mehrere vertikale, jeweils testbare Pakete zerlegt werden.

>    WP-09.3 als Adapter über den neuen Vertrag umsetzen und erst danach WP-09.4 starten. Das verhindert, dass GTK eigene Semantik für Progress, Fehler oder Teilresultate entwickelt.

## Consolidated Findings

The three reviews agree on the following points:

1. The read-side architecture is mature enough to support the next phase.
2. The GUI's unverified asynchronous JSON-filter change must be completed and
   verified before it is treated as finished.
3. WP-08 contains useful, bounded test gaps and should remain separate from
   feature implementation.
4. WP-09.1 is the correct architectural starting point, but it must define
   commit boundaries, terminal outcomes, callback ownership, and mode-specific
   request semantics rather than only introduce a cancellation flag.
5. WP-09.2 must be decomposed into independently testable vertical slices.
6. The CLI should become the first consumer of the shared operation contract;
   GTK should follow after the CLI behavior is a reference implementation.
7. Repository write serialization and network-filesystem support are separate
   concerns and must not be hidden inside the first operation implementation.

## Open Questions For External Reviews

- Should WP-08 be completed fully before WP-09.1, or should WP-08 and the
  contract design proceed in parallel?
- What cancellation policy is preferable for each operation: rollback,
  checkpointed partial commit, or operation-specific semantics?
- Should repository write serialization live in the backend Repository API, in a
  process-level operation manager, or in both layers?
- Should JSON and SQLite share one operation request type with explicit target
  variants, or use separate request types behind one operation interface?
- Is the GUI P0 worth finishing before backend contract design, or should only
   its verification be completed while WP-09.1 starts in parallel?

## Consolidated Findings Update After Review D

The new independent review confirms and sharpens earlier findings, with three
additional concrete defects that were not previously named:

1. **Scanner correctness defect** at `repository/scanner.d:126`–`139`:
   `markMissing` iterates a live SQLite cursor and issues `UPDATE` statements
   on the same table it is reading. This is a fragile iteration pattern that
   SQLite does not guarantee to be safe for mutation during read.
2. **Blob growth without cleanup** at `repository/scanner.d:106`–`115`: When
   a file's size or mtime changes, a new blob row is inserted and the file
   reference is reattached; the previous blob is left as an orphan. Orphan
   removal only happens via `analysis.d` or `dropMissing`, so repeated scans
   of volatile directories inflate `blobCount`.
3. **Case-sensitivity parity gap** between the tree/file filter path and the
   blob/catalog filter path: `RepositoryQueryOptions` (`types.d:322`–`350`)
   has no `caseSensitive` field and `prepareCatalogQuery` uses hard
   `lower(...)`. This contradicts the `README.md` claim of full JSON/SQLite
   case-sensitive filtering parity.
4. The `docs/ARCHITECTURE.md` module-dependency diagram (section 8) does not
   include the `repository/` subtree. New contributors will not see the
   actual SQLite layering from the diagram.
5. `WP-00` is still marked `[-]` although WP-02 through WP-07 are complete.
   The compatibility decision matrix and GUI baseline records that WP-00 was
   supposed to freeze are not checked off anywhere else.

## Status as of 2026-11-16

The reviews above are historical. This section records what has since been
fixed, what changed by design, and what is still open. Each entry was verified
against the current working trees.

### Fixed

- **GUI async filter lifecycle (reviews A, B, D).** Asynchronous loading and
  filtering now use request IDs and lifecycle guards; late replies cannot
  overwrite a cleared, switched, or cancelled selection. The GUI TODO no longer
  lists this as in progress.
- **Case-sensitivity parity (review D.1 items 1, D.2 section 2).**
  `RepositoryQueryOptions` has a `caseSensitive` field and the catalog query
  builders honor it; the GUI `SourceQuery` exposes the same flag. The blob
  table and the tree/file filter now share one semantic.
- **Genuine `dataVersion: 2` fixture (WP-08.2).**
  `test/json_file_wrapper_v2.json` contains `"dataVersion": 2` and covers the
  wrapper import path. `test/json_file_v2.json` keeps its historical file name
  but remains a `dataVersion: 3` document, as documented in the fixture notes.
- **Scanner correctness (review D.1 item 3, D.2 section 3).** The scan now
  stages missing references (`stageMissingReferences`) and applies them in the
  catalog transaction (`applyStagedMissing`); it no longer mutates the table it
  iterates. `deleteUnreachableBlobs` runs inside the same transaction, so
  repeated scans of volatile directories no longer inflate the blob table.
- **Cancellation and progress (reviews A, B, C, D).** The shared operation API
  (`OperationControl`, `OperationPhase`, `runOperation`) exists and is used by
  CLI and GUI. Deep archive scans support pause, cancellation at member
  granularity, and resumable partial indexes.
- **Directory-source connection churn (review D.1 item 2, D.2 section 1).** The
  GUI no longer opens a `Repository` per tree call; it talks to the
  storage-neutral `CatalogBackend` through `model/catalogsource.d`.
- **Network filesystem safety (review D.2 section 5.2).** Repositories on
  sshfs/FUSE, SMB/CIFS, NFS, and 9p mounts are rejected before opening with a
  clear error; shipped in GUI 0.13.1.
- **Architecture documentation (review D.2 section 5.5).** `ARCHITECTURE.md`
  documents the `repository/` subtree and the storage-neutral operation runner.
- **WP-00 baseline (review D.2 section 6).** WP-00 is checked off with completed
  steps in `docs/SQLITE-IMPLEMENTATION-PLAN.md`.

### Changed by design

- **DTO opacity (review D.1 item 5, D.2 section 1).** The blob/catalog path
  still returns `NamedBinaryBlob[]`. Replacing it with opaque DTOs belongs to
  the Major 27 format cleanup, which is deliberately deferred to 2027. The
  repository API therefore remains domain-typed for now.

### Still open

  performance are covered by `scripts/benchmark-filters.sh`, but the per-batch
  render profile on a real display is an open P1 item.
- **Preview and splitter layout issues (reviews A, D.2).** The splitter
